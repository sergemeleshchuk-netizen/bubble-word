## 1. Как считается сейчас

`tool/level-tool/web/src/core/levelMath.ts:46`

```
пол   = 3 × категорий + распилов        минимум ходов идеальному игроку
лимит = ceil(пол × K),  K ∈ [1.25, 1.6]
```

`K` назначается ролью уровня в кривой — `blockPlan.ts:189`:

| роль | K | | роль | K |
|---|---|---|---|---|
| передышка | 1.60 | | рост | 1.35 |
| выход | 1.50 | | спайк | 1.30 |
| вход | 1.45 | | пик | 1.25 |

туториал — `null` (без лимита).

Два свойства этой формулы, и оба оказались неверными:

1. **Запас на ошибки задан в процентах от длины уровня** (множитель), а не в
   ходах.
2. **Запас назначен на глаз**, по роли. При том что цена ошибок у нас уже
   измеряется — см. §3.

## 3. Что говорит наш слепой бот (замер, повторять не надо)

Слепой бот (`core/simulateBlindPlay.ts`) уже меряет цену неверных перетаскиваний
в ходах: `missesMedian` / `missesP90`, доля прогонов с победой `winRate` и
`errorBudgetUsed` = промахи p90 ÷ запас зрячего бота.

Скрипт разбора: **`scripts/check_move_limit.ts`** (написан для этого разбора,
лежит в репозитории). Запуск: `node scripts/check_move_limit.ts`.

Результат на 03.08:

| декада | бюджет ошибок съеден | winRate |
|---|---|---|
| 1-10 | 0.00 – 0.78 | 92–100% |
| 11-20 | до **2.54** | у L12 — **0%** |
| 51-60 | до **4.75** | у L54, L60 — **0%** |
| 121-130 | до **6.62** | у L125 — **0%** |

`errorBudgetUsed > 1` означает: живой игрок в лимит не уложится. У половины
уровней после двадцатого — не уложится. **Жалоба владельца продукта («мне не
хватает ходов») подтверждена нашим же измерением.**

Почему это не влияло ни на что: в `generateBlock.ts:270` записано, что слепой
бот «ни на что в приёмке не влияет» — модель знания игрока не откалибрована, и
ей осознанно не доверили решать судьбу уровня. Число считалось и показывалось,
но в лимит не заходило.

## 4. Что делать

Решение владельца продукта 03.08: переходим на **аддитивный запас, измеренный,
а не угаданный**.

```
лимит = пол + запас
запас = max( базовый(пол, роль), промахи_p90 + 2 )
```

**Базовый запас** повторяет ступень оригинала: 15 при поле ≤ 32, 10 при поле
больше; роль двигает на ±2 (пик теснее, передышка просторнее). Это чинит зажим
на маленьких уровнях.

**Пол по промахам** делает бюджет ошибок измеренным. Слепой бот к тому же
оптимистичен — он не моделирует вместимость поля, то есть видит больше
вариантов, чем живой игрок (это записано в шапке его модуля). Значит его p90 —
оценка снизу, и брать её как минимум безопасно.

**Предохранитель — обязателен.** У L125 промахи p90 = 86 при поле 48; поднять
лимит до 136 было бы абсурдом. Если измеренная цена требует запаса больше
полутора базовых — виноват не лимит, а **уровень**: в нём слишком много
незнакомых слов. Такой уровень браковать и пересобирать, а не расширять ему
лимит. Это и превращает `winRate` слепого бота из справочного числа в гейт
приёмки — то, ради чего его писали.

Порог «полторы базовых» подобран на глаз и сам подлежит наигровке: вынеси его
именованной константой рядом с формулой, а не числом по месту.

Владелец продукта просил делать формулу и гейт **вместе**.

## 5. Файлы, которые придётся тронуть

| файл | что там |
|---|---|
| `web/src/core/levelMath.ts:46` | сама формула `moveLimit`, константы K |
| `web/src/core/blockPlan.ts:189` | назначение K по роли → станет базовым запасом |
| `web/src/core/generator.ts:1529` | применение лимита при сборке уровня |
| `web/src/core/generateBlock.ts:270` | там слепой бот считается ПОСЛЕ уровня — а для гейта нужен ДО или в цикле пересборки |
| `web/src/core/scoringDifficulty.ts:318` | «теснота» читает `moveLimitK` |
| `web/src/core/playableModifiers.ts:346` | пересчёт лимита под модификатор |
| `scripts/pack_to_handoff.py:84` | та же формула на питоне, для пакетов пайплайна |

Порядок вычислений — главная засада. Сейчас лимит ставится при сборке уровня, а
слепой бот запускается уже по готовому уровню. Если запас зависит от промахов,
появляется цикл: лимит → бот → лимит. Разорвать можно так: собрать уровень с
базовым запасом, прогнать бота, при нужде поднять запас и переоценить. Второй
прогон бота с новым лимитом нужен только для `winRate` — сами промахи от лимита
не зависят.

## 6. Что сломается, и это нормально

- **Оценки D сдвинутся.** Фактор «теснота» выражен через `moveLimitK`; его надо
  переписать на долю запаса `запас/пол`. Смысл тот же, шкала другая — пересчитай
  сданные блоки через `scripts/rescore_block.ts`.
- **Хеши уровней изменятся** → поднять `GENERATOR_VERSION` (сейчас `gen-1.5`) с
  записью в шапке `generator.ts`, поднять `TOOL_VERSION` и написать строку в
  `CHANGELOG.md` (без строки тест не пропустит).
- **`moveLimitK` из спека НЕ убирай** — сделай его производным `лимит/пол`. Так
  уже устроено для уровней оригинала (`referenceLevels.ts:256`), и формат
  передачи в прототип (`move_limit_k`) не поломается.
- **Пакеты надо пересобрать** и заново прогнать симуляторы.
- Тесты, которые заденет: `decade`, `determinism`, `scoring`, `playability`,
  `blind_play`, `deal_scheme`. Гейт `playability` требует, чтобы каждый принятый
  уровень доигрывался в лимит — он должен остаться зелёным.

## 7. Как проверять

```bash
cd tool/level-tool
npx tsc --noEmit
npm test                                   # должно быть 0 падений
node scripts/check_move_limit.ts           # бюджет ошибок ≤ 1 и winRate 100%
node scripts/simulate_play.ts --all        # все выложенные уровни проходятся
node scripts/check_reference_levels.ts 1-20
```

Приёмка по существу: в `check_move_limit.ts` у ВСЕХ уровней
`errorBudgetUsed ≤ 1.0` и `winRate = 100%`. Сейчас это не так — см. §3.

Отдельно сверься с оригиналом: собери уровни из источника RefBWJ и посмотри, что
новая формула на их полах даёт числа, близкие к записанным (§2). Совпадать
байт-в-байт не обязано — у них своя рука, — но ступень 15/10 должна читаться.

И правило проекта: **«готово» говорим только после проверки в реальном
браузере**. Прототип — `site/playable/index.html`, он один; уровень открывается
как `?level=<путь к json>` или через `localStorage` + `?gen=N`.
