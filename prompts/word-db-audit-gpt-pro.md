# Кейс промптинга: внешний аудит базы слов через ChatGPT Pro

**Дата:** 31.07.2026
**Модель-аудитор:** ChatGPT Pro (взята как самая сильная доступная модель
для «холодного» ревью — свежий взгляд без контекста нашей разработки)
**Модель-исполнитель:** Claude Code (Opus 5) — правит pipeline и данные
**Точка отсчёта в репозитории:** коммит `2a304d1`
**Материалы аудита:** `prompts/word-db-audit-pack/` (распакованный
`word_database_audit_pack.zip`)

---

## Зачем этот кейс сохранён

Схема «одна модель делает, другая независимо проверяет» дала результат,
который наш собственный pipeline не находил: он проверял себя своими же
метриками. Внешний аудитор получил только *выдачу* (снимок SQLite +
человекочитаемый ревью-пак) и нашёл расхождения между тем, что база
заявляет, и тем, что в ней реально лежит.

Что сработало в промптинге:

1. **Аудитору дали артефакт-выдачу, а не код.** На вход ушла папка
   `БАЗА-СЛОВ/` (снимок `база-слов.sqlite` + `ревью/00…05_*`), то есть
   ровно то, что увидел бы заказчик. Модель не могла «поверить» коду —
   ей пришлось сверять цифры между файлами. Именно так вылезло, что
   `04_flags.md` показывает 60 проблемных категорий вместо 86.
2. **Просили не мнение, а машиночитаемые списки.** Аудит вернулся как
   таблицы (16 файлов: CSV + XLSX + два MD), где каждое замечание —
   строка с идентификаторами. Исполнителю не нужно переспрашивать
   «а какие именно категории» — он берёт список и правит.
3. **Три уровня детализации в одном паке:** RU-резюме с приоритетами →
   XLSX с конкретикой → технический MD с методикой. Промпт исполнителю
   прямо задаёт порядок чтения, поэтому он не тонет в 1.3 МБ таблиц.
4. **Приоритеты P0/P1/P2 задал аудитор, а не исполнитель.** Это снимает
   у исполнителя соблазн начать с приятного и лёгкого.
5. **В промпте исполнителю явно зафиксированы инварианты проекта**
   (source of truth — текстовые seed-файлы, SQLite пересобирается,
   экспортированный снимок руками не трогаем). Без этого агент начал бы
   править `.sqlite` напрямую — быстро и неправильно.
6. **Явное разрешение спорить.** «Не принимай автоматически каждое
   замечание, для спорных семантических случаев сформируй отдельный
   список на ручное решение» — иначе агент чинит семантику по чужому
   мнению и ломает то, что было верным.
7. **Порядок работы прописан шагами** (изучи → сопоставь с кодом →
   план по файлам → и только потом реализация → отчёт). Для задачи на
   ~десяток файлов это заметно снижает шанс хаотичных правок.

## Что аудит нашёл (сводка)

Технически файл здоров: `PRAGMA integrity_check = ok`, 0 нарушений FK,
`05_memberships.csv` совпадает с SQLite построчно (17 550 строк).
Вывод аудитора: **база пригодна как кандидатный граф «слово — значение —
категория», но не как автономный production-источник для генерации.**

Ключевые цифры (полностью — `word-db-audit-pack/audit_summary.csv`):

| Что | Сколько |
|---|---|
| Слов / категорий / связей / значений | 10 005 / 1 092 / 17 550 / 549 |
| `approved` при `familiarity_score IS NULL` | 20 связей (26 слов) |
| Связей многозначных слов без `sense_id` | 96 (18 слов) |
| Часто переиспользуемых слов без значений вообще | 736 |
| Пар категорий с ≥4 общими игровыми словами | 516 (в них 526 категорий) |
| Категорий, не собирающих четвёрку без `hard_only` | 34 (из них 13 — вообще без normal-пула) |
| Категорий, недосчитанных в `04_flags.md` | 26 (60 вместо 86) |
| Связей с одинаковым `fit_score = 0.97` | 17 489 |
| Связей `hard_only` при `obviousness ≥ 0.80` | 355 |

Смысловое ядро претензий:

- **нет проверенных игровых четвёрок** — есть пулы, а четвёрка из пула
  не гарантирует единственного решения (`JEWELRY STONES` и `GEMSTONES`
  делят 15 слов);
- **скоринг слепил в одну шкалу разные вещи** — семантическую
  корректность, знакомость слова, очевидность значения и игровую
  сложность; статусы считались относительно других категорий того же
  слова, без абсолютных порогов (отсюда `xylophone → MUSICAL INSTRUMENTS`
  в `hard_only`);
- **`NULL` проходил как подтверждение**, а не как «нужно ревью»;
- **отчёт для человека расходился с базой** — `04_flags.md` занижал
  число проблемных категорий.

## Промпт, который пошёл исполнителю (verbatim)

```text
Я передаю аудит базы слов: word_database_audit_pack.zip.

Исходное состояние проекта находится в коммите 2a304d1.
Распакуй архив и изучи в таком порядке:

1. word_database_audit_RU.md — основной вывод и приоритеты.
2. word_database_audit.xlsx — конкретные проблемные категории, связи и списки.
3. word_database_audit.md — технические детали и методика проверки.

Задача: исправить базу и pipeline по результатам аудита.

Работай по приоритетам:

P0:
- запретить automatic approved при familiarity_score IS NULL;
- закрыть связи многозначных слов с отсутствующим sense_id;
- подготовить механизм поиска слов, которым нужны дополнительные senses;
- исправить генерацию 04_flags.md;
- добавить проверку пригодности категории для сборки группы из 4 слов;
- добавить проверку конфликтов и неоднозначных пересечений категорий;
- исправить подтверждённые семантические ошибки из audit-файлов;
- отключить категории, которые не могут собрать нормальную четвёрку.

P1:
- разделить semantic correctness, familiarity, obviousness и gameplay difficulty;
- добавить слой проверенных игровых четвёрок;
- добавить solver, который принимает уровень только при единственном корректном разбиении;
- добавить category conflicts / pairing restrictions;
- добавить readiness status для категорий.

Важно:
- source of truth остаётся в текстовых seed-файлах и review_decisions.csv;
- SQLite должен по-прежнему пересобираться из текстовых источников;
- не редактируй только экспортированный база-слов.sqlite;
- все исправления должны вноситься в pipeline и source-файлы;
- не принимай автоматически каждое замечание из аудита: для спорных
  семантических случаев сформируй отдельный список на ручное решение;
- после изменений пересобери базу, запусти integrity checks и повторно
  сгенерируй review pack.

Сначала:
1. изучи аудит;
2. сопоставь замечания с текущим кодом и данными;
3. составь developer-ready план изменений по файлам;
4. только затем приступай к реализации;
5. в конце предоставь список исправленного, оставшихся ручных решений
   и результаты проверок.
```

## Шаблон для переиспользования

Приём переносится на любой «пакет данных, который мы сдаём наружу»:

1. Собрать **выдачу как её увидит заказчик** (снимок + человекочитаемый
   ревью-пак), без исходников pipeline.
2. Скормить сильной внешней модели с запросом: структурная проверка +
   целевая семантическая, **вывод таблицами** (по файлу на класс проблем),
   приоритеты P0/P1/P2, критерии готовности.
3. Промпт исполнителю строить из: порядок чтения материалов → приоритеты
   → **инварианты проекта** (что нельзя трогать) → право не соглашаться со
   спорными пунктами → шаги (изучить, сопоставить с кодом, план, реализация,
   отчёт).

Ограничение, которое аудитор честно назвал сам: проверка структурная и
точечно-семантическая, «это не утверждение, что все 17 550 связей вручную
проверены носителем английского языка». Native-speaker review всех
`approved` остался отдельной задачей (P1).
